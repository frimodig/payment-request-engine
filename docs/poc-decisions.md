# Decision log

Decisions taken while building the proof of concept, with the reason for each, in the order they were made. Items 1 to 13 were made in an unattended overnight run and reviewed afterwards; later items follow the code reviews and the choices made on them. The design as it stands is in [architecture.md](architecture.md); open gaps are in [poc-limits.md](poc-limits.md); the review findings and what became of them are in [review-findings.md](review-findings.md).

To run the checks you need JDK 21 and Docker; see the README.

1. State machine takes and returns a `Context(state, position, cancelRequested)`. `position` is the last known downstream state (SENDING/PRESENTED/ACCEPTED), kept across UNKNOWN and CANCELLATION_REQUESTED. Needs migration V2 (two columns on payment_request). Why: checker round 2 showed forgetting position gave wrong results after a timeout.
2. All effects are persisted as `outbox` rows in the same transaction (kind = effect type), which resolves the doc conflict and the "lost after commit" gap. Dispatching: only PartnerStatus is a partner delivery; others are internal kinds. No dispatcher is built in the PoC.
3. Partner-visible states: PRESENTED, ACCEPTED, CANCELLATION_REQUESTED, PAID, REJECTED, REFUSED, EXPIRED, CANCELLED.
4. Contradicting final event on a terminal payment: STALE plus RaiseAlert.
5. Cancel on UNKNOWN is forwarded (CANCELLATION_REQUESTED) unless the position is ACCEPTED (too late).
6. Money constructor validates the ISO currency, like parse.
7. Worker design: one claim = pending provider events, then pending cancellations, then at most one timed step; each fenced write renews the lease; lease released only after success (a failure leaves it to expire, like a crash).
8. Every effect, including internal ones (reconciliation, alerts, forward cancellation), is an `outbox` row written in the same transaction (docs/database.md updated). Nothing dispatches them.
9. After a send fails or times out the worker asks the downstream for status by idempotency key: Known -> record the reference and keep waiting; otherwise UNKNOWN + reconciliation row. Silence after a known reference -> UNKNOWN. NotFound on takeover -> resend under the SAME key (key = payment id + attempt).
10. A step that leaves the state unchanged (stale event, position update) never moves the due time, so repeated events cannot postpone a timeout.
11. Provider events are matched by downstream reference only; events for a payment that timed out before its reference was known stay PARKED (poc-limits.md).
12. Fake downstream lives in src/main (can back a demo); tests mutated: removing the lease-token fence, using a random idempotency key and ignoring leases were each caught (the fence one needed an extra test, added).
13. Used a checker agent instead of /code-review for slices 2-4: the files are untracked, so there is no git diff for the skill to review.

14. Checker round on slices 2-4 found: takeover via a cancellation input could lose the downstream reference (fixed: learn the reference by status query before acting on an input, and before timing out CANCELLATION_REQUESTED/PRESENTED/ACCEPTED); inbox/relink race (fixed: per-reference advisory lock in receive and in the reference-storing transaction); concurrent resends deadlocked (fixed: insert in sorted order, results in caller order); unescaped JSON from downstream reason codes (fixed: jsonString); missing event_seq fence test (added). Each fix has a test and each test was shown to fail when its fix is removed.
15. Not done: /code-review (files untracked, no diff) and a re-check agent on the final fixes. Recommend running /code-review high after reviewing and staging.

16. After the first /code-review (high), the user took all proposed fixes: reason codes are cleaned and bounded; the claim order uses COALESCE(next_action_at, created_at) so inputs on waiting payments are not starved; an unavailable status query is retried (3 times, 30 s apart) before UNKNOWN; reference bookkeeping events are TECHNICAL; scheduleFor derives from State.hasAutomaticWork/waitsForDownstream; CLAUDE.md heading, Main.kt text and poc-limits updated. Pool and test-seam findings are recorded as limits only.

17. Second /code-review (high, main..HEAD): fixed input-first claim order (inputs before any timer, whatever the due time), per-outage retry counting, rollback no longer hides the cause, length-prefixed content hash, wrapper checksum pinned (value from services.gradle.org, matched against the downloaded zip), `/bin/` ignore. Due-time reset on input-only learnReference: fixed without a behaviour test, since every reachable input also changes the state and the due time with it. Cancellation refusal stays a documented limit (needs a new partner status).

18. Final /code-review max, then the user chose: fix the first five findings, document the rest, work straight on main, update the architecture from the PoC, document the DB structure. Done: status check before timeout (alive keeps waiting, silence retries then UNKNOWN), overdue SENDING checked before a cancellation, NotFound with a stored reference goes UNKNOWN instead of resending, unusable/duplicate references and throwing status calls end in UNKNOWN, CANCELLED confirmation refused once position is ACCEPTED. Pushed to origin/main as 9d89a7d and 2f67fde (92 tests green).

19. An adversarial review of the plan, with the brief kept general on purpose (the user's framing). The user's choices: separate PAID from SETTLED in the docs and the PoC; explore outage recovery and build the most promising option; fix the doc claims the review refuted; write a threat model; end-to-end ids are unique per partner for good, as a published rule; financial-record retention protects payment data from erasure for the legal period only.
20. Outage recovery: back off per payment up to an outage horizon (2 h default) instead of three fixed retries, which item 16 introduced. A failed send the downstream never saw and an unanswered status query are both outage events; UNKNOWN only once the outage outlasts the horizon. Chosen over a circuit breaker (next step), UNKNOWN re-checking itself (later safety net) and bulk reconciliation (belongs to reconciliation). No new state, no schema change.
21. PAID waits for settlement with no timer; SETTLED is terminal and confirmed by reconciliation. SETTLED is partner-visible. A PAID payment keeps ACCEPTED as its stored position (the state machine treats PAID itself as the position), so the V2 CHECK on downstream_position is unchanged. A different outcome after PAID is a MISMATCH; a contradicting outcome after SETTLED is stale with an alert.
22. Partner webhook URLs are checked by WebhookTarget: https, fully qualified host names only (no IP literals), every resolved address public. Built as a standalone check because nothing delivers webhooks yet. Ports are not limited; the user accepted that as a documented gap.
23. Left documented on purpose (user's choice): unlimited webhook ports; a cancelled payment the downstream never received ends in UNKNOWN; the PoC does not recover without a status endpoint. Recovery with and without a status endpoint, and every cause of manual work, are in recovery.md.
24. A re-check of the review fixes found that a status answer reporting nothing new did not end an outage, so a short outage hours after another one sent payments straight to UNKNOWN. Fixed: a status answer that finds the payment ends an outage; a repeated webhook still does not. A send endpoint that stays down while status queries answer "not found" is still one outage, and reaches UNKNOWN at the horizon. 120 tests.

25. Warm-up after an outage and jitter on the backoff are part of the design, not built.
26. A second adversarial review of the plan (three challengers: operations, payment domain, security and scale) found 23 gaps. The user took every recommendation on the open questions: two synchronous standbys with quorum commit; a running total of credits instead of exact-amount-only; NOT_PAID and PAID_LATE as partner statuses and an under-review flag; reading the partner's statements as a condition of onboarding; file partners can cancel in Phase 1; a hash chain per payment for tamper evidence; only (partner, end-to-end id) kept after the legal period; the downstream key derived from the partner's own ids. All answers are designs in architecture.md; review-findings.md lists them.
27. Kafka as the only store would avoid a dual write, but adds a dependency for little value because the status API, due times and reconciliation need a queryable database anyway. The deck and study guide give that reason instead of "dual write".

28. A third review of the plan (two reviewers: is it coherent, and does it make sense as one design) found that the review answers had been added beside the old text and contradicted it. The user approved items 29 to 38 and a rewrite of the plan, not more patches. Findings and outcomes are in review-findings.md.
29. First-release cut. The pilot is one partner, one downstream with a status endpoint and one front door. It holds what cannot be retrofitted and what protects money; everything else is added when its trigger arrives (the API ships, a second partner, a second or fragile downstream, a non-synchronous downstream, later). architecture.md's Delivery section holds the cut, and recovery.md and threat-model.md tag each designed row R1 or later.
30. architecture.md restructured to one argument with a key-decisions table, a "files end to end" section, an API sketch, one table of states and partner statuses, and settlement merged into one section. Reference detail moved to one home each: availability, partitioning, retention and integrity to database.md; SSRF, signing and XML hardening to threat-model.md; outages, warm-up and the restore runbook to recovery.md; gates, manual actions, queues, alerts, deploys, scheduled jobs and the platform to a new operations.md.
31. Partitioning: only `payment_event` is partitioned on day one, by the payment's creation month, with no default partition and partitions at least three months ahead. Every other table, the deduplication key table included, stays unpartitioned with batched deletes, and is partitioned later only if measured. Revises the second review's partitioning answer (item 26: every table by creation month), which broke parked events and global uniqueness.
32. One gate concept: a row per downstream, per partner and one global, holding pause, maintenance window, circuit state, send rate and an in-progress limit (called in-flight in the review; renamed because "in flight" already means sent and not yet answered). A gate blocks only the send step, never status queries, inputs or timers. The in-progress limit counts unexpired leases, never a counter. The routed downstream is stored at `READY_TO_SEND`. The circuit breaker and warm-up come after the first release. Revises item 25 (warm-up stays designed, now later) and the second review's pause, kill switch and per-partner counter (item 26).
33. The outage horizon applies only to payments that may need a resend (no stored reference, or the downstream says it has nothing). An acknowledged payment keeps backing off at the cap while the downstream's outage alert tells a person; it never goes to `UNKNOWN` because of an outage alone. "`UNKNOWN` re-checks itself" is no longer the outage safety net; it stays as a later option with a smaller job (ask once after an outage). Partly revises item 20.
34. Pauses, the kill switch and declared maintenance windows freeze the horizon, but the time since a payment's first possibly-delivered send must stay inside the downstream's key retention; a payment that would cross it goes to `UNKNOWN` even while frozen. Revises the second review's maintenance-window freeze (item 26).
35. The hash chain moves after the first release. The first release has column grants, append-only grants, the deferred trigger and the daily consistency job; threat-model.md names the threat the chain answers, a DBA or superuser. Revises the sequencing of item 26's hash chain, not the decision.
36. Payments still not final when their month nears the end of the legal period are escalated to their queue owner before that date; the month is dropped once they are resolved, and an alert fires otherwise. Refines item 19's retention rule.
37. Partners without statement access are onboarded only by exception; their contract makes `PAID` final, with no settlement deadline, and `PAID` counts as final for retention. Refines item 26's "statements a condition of onboarding".
38. The not-paid deadline asks the downstream first, under the outage rules. With no credit and no later state the payment moves to `NOT_PAID`; with a partial credit, to `MISMATCH`. A late `PAID` provider event, or a matched credit, after a not-paid final state moves it to `PAID_LATE`. Revises item 26's `NOT_PAID` rule, and items 4 and 21 for `PAID` after `CANCELLED`.
39. Choices the rewrite made, confirmed by the user: `PAID` has a settlement deadline (the `PAID` time plus a per-route number of business days), and no money or a total still short by then is a `MISMATCH`; this revises item 21's "no timer". The attempt number increments only through an approved manual resend after the downstream confirmed the earlier attempt ended without payment. Closing a quarantined payment gives `REJECTED` if it was never sent, otherwise `UNKNOWN`.
40. After the rewrite's re-check: a database restore writes one `RESTORED` event per affected payment, the only allowed jump in its event sequence, using a delivery log the dispatcher keeps outside the database. For a partner onboarded without statement access, `PAID_LATE` is final like `PAID`. A quarantined payment is claimed only to apply an approved manual action, and a held-file decision is applied by ingestion to the submission.
41. Contests (disputes, recalls, chargebacks) are out of scope on purpose: a separate disputes and returns flow handles them. The engine records a contest as a linked record against the payment, which never moves backwards; an open linked record holds back retention.
